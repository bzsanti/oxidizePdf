## Hallazgos

Las líneas corresponden al HEAD del PR, no al checkout actual.

1. **La nueva API descarta los diagnósticos**: `oxidize-pdf-core/src/text/extraction.rs:1295` elimina RecoveryContext después de extraer. El helper puede omitir un Form completamente corrupto y devolver solo PageBodyText como éxito ordinario, sin indicar pérdida. Solución: usar `extract_from_page_with_recovery(&doc, page, max_stream_bytes)` y devolver su RecoveredText; si se conserva una API adicional, debe exponer diagnósticos por página y tener pruebas de omisión y recuperación, incluida la extracción multipágina. El booleano truncated mide el presupuesto de texto y no sustituye esos diagnósticos.
2. **El presupuesto de texto se usa como límite de descompresión**: `oxidize-pdf-core/src/text/extraction.rs:1287` hace que un PDF válido con dos caracteres falle bajo un presupuesto de ocho bytes porque sus operadores PDF ocupan más. Solución: recibir/configurar max_stream_bytes por separado, como hace la API existente, manteniendo max_extracted_bytes exclusivamente para la salida. Añadir el contraejemplo válido, presupuesto cero y controles de límite de stream.
3. **Se retienen dos buffers descomprimidos simultáneamente**: `oxidize-pdf-core/src/parser/filters/recovery.rs:161` mantiene first_partial mientras el segundo inflate construye otra salida. Para 1 MiB recuperado se mide un incremento adicional exacto de 1 MiB frente a la base. El límite por salida no es un límite agregado de memoria. Solución: conservar el descarte anterior salvo que un fixture demuestre necesidad del fallback; si resulta necesario, reutilizar/acotar almacenamiento y probar su pico. No basta con ampliar el cap ni con llamar a ambas salidas individualmente acotadas.
4. **Rustdoc promete activación automática inexistente**: `oxidize-pdf-core/src/text/extraction.rs:810` dice que lenient/tolerant activa recuperación; el despacho de la línea 1284 solo consulta el builder y los tests del propio PR esperan error sin activarlo. Solución: documentar opt-in explícito y enlazar la API con diagnósticos; no cambiar el modo ordinario para satisfacer una descripción contradictoria con #637.
5. **Las pruebas no demuestran el cambio del decoder**: `oxidize-pdf-core/tests/issue_680_flate_stream_recovery_test.rs:40` aprueba sin el cambio de recovery.rs, al igual que los otros dos tests. Las aserciones parciales de texto tampoco comprueban el diagnóstico ni toda la salida recuperada. Solución: aportar una entrada que falle por la pérdida de first.partial en la base y pase con la corrección, con bytes/diagnóstico exactos y límite fatal; o retirar el cambio innecesario. Mantener los escenarios de página/Form y fortalecer sus aserciones sobre la API observable.

Los cinco hallazgos corresponden al alcance de #680/#682. No se abren tareas
correctivas de subsistemas independientes. La base main y el conflicto de TASKS
son condiciones de integración, no un sexto defecto funcional.

## Corrección de los cinco hallazgos

El usuario solicitó explícitamente corregir los hallazgos. El candidato conserva
los dos commits del autor y añade las correcciones sobre su rama, sin modificar
los cambios locales ajenos. Se retiraron el builder sin diagnósticos y el fallback
que retenía first.partial. El código ejecutable queda idéntico a main; el diff
final frente a esa base contiene documentación y pruebas. Esto no introduce
recuperación automática ni una nueva API: muestra cómo usar la API pública
existente para resolver el caso de uso de #680 de forma observable.

| Hallazgo | Corrección y evidencia de cierre |
| --- | --- |
| Diagnósticos borrados | Se usa RecoveredText; tests de página, Form, omisión y prefijo comprueban acción, ubicación y salida. Mutación que vacía diagnósticos provoca cinco fallos de aserción |
| Límites confundidos | Presupuesto de texto 0/1/8 independiente del límite de stream; texto OK en PDF válido y dañado. Mutación que vuelve a usar max_extracted_bytes para el stream falla. Límite fatal se prueba en Contents y en Form con página invocadora de seis bytes |
| Dos buffers expandidos | Se restablece drop(first.partial). Nueva prueba de allocator falla sobre PR original (2.140.544 bytes) y pasa corregida (1.091.968), salida 1 MiB. No mide RSS |
| Documentación contradictoria | Se elimina el builder; rustdoc ordinario enlaza la API explícita. Ejemplo no_run compila y conserva diagnósticos; tests strict/tolerant/lenient confirman opt-in |
| Falta de discriminación | Se retira la modificación del decoder no demostrada. Siete contratos con bytes/texto/diagnósticos precisos y una prueba de memoria; RED/GREEN real y dos mutaciones funcionales detectadas |

Validación de implementación: 42/42 pruebas focalizadas sobre main y 42/42
