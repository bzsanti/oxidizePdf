# Review #733 — DeviceCMYK is not RGBA

Issue: #733 — fix(images): avoid exporting CMYK samples as RGBA — https://github.com/bzsanti/oxidizePdf/issues/733

Eight-bit DeviceCMYK samples are converted to opaque RGB using unmanaged subtractive device conversion. Black ink never becomes alpha. An independent soft mask remains alpha after conversion. Other four-component source paths return an explicit unsupported error instead of writing fictitious RGBA. This does not implement ICC color management or claim conversion of Indexed-CMYK or 16-bit CMYK.

## Evidence and manual review

Public hand-built PDF fixtures contain literal cyan, black, white, red and intermediate sample values. Extracted PNGs are decoded with the independent image crate. Literal expected RGBA output distinguishes K from transparency; separate masks and a legitimate RGB-alpha control exercise the alpha boundary. Truncated samples and unsupported depth/Indexed-CMYK return errors. Initial RED: four failures, two controls pass. Final: six new contracts and 22 related image integration tests pass; strict all-target Clippy with external-images passes.

Review followed indirect ColorSpace resolution, component count, minimum byte count, conversion, soft-mask composition and PNG color-type selection. Four-component guard applies before either branch of encoding. Device conversion arithmetic fits u16 (maximum 65025 plus rounding 127). Expected sample length uses checked usize multiplication before slicing and allocation. Existing in-memory pixel limits remain in force. No public type or dependency changes, new unsafe code, or production external command.
